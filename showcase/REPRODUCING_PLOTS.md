# Reproducing the Showcase Plots

This note records the important steps behind the curated figures in this
folder: what was compared, which data shape is required, and which project
functions are involved.

The short version is:

1. Download forecasts and observations for the same location/time range.
2. Normalize both into local Parquet partitions.
3. Build a verification table by joining forecast target time to observation
   time.
4. Compute error columns and grouped metrics.
5. For spatial figures, repeat the same workflow over a grid of nearby points.
6. Compare native-grid verification with forecasts interpolated onto the
   observation grid.
7. Render either standard CLI plots or curated composite figures from those
   verification/metric tables.

## Core Data Flow

### 1. Download

The basic point workflow uses:

- `downloader.api.fetch_observations()`
- `downloader.api.fetch_single_run()`
- `downloader.normalize.json_to_observation_df()`
- `downloader.normalize.json_to_forecast_df()`
- `downloader.storage.write_observations()`
- `downloader.storage.write_forecasts()`

Example:

```bash
meteoright download \
  --lat 55.605 --lon 12.574 \
  --start 2026-05-20 --end 2026-05-22 \
  --type observations \
  --variables temperature_2m,precipitation,wind_speed_10m \
  --output data/copenhagen_demo

meteoright download \
  --lat 55.605 --lon 12.574 \
  --start 2026-05-20 --end 2026-05-22 \
  --type forecast \
  --model ecmwf_ifs_single \
  --variables temperature_2m,precipitation,wind_speed_10m \
  --output data/copenhagen_demo
```

For self-hosted Open-Meteo, point the command at the backend:

```bash
meteoright download \
  --lat 55.605 --lon 12.574 \
  --start 2026-05-20 --end 2026-05-22 \
  --type observations \
  --variables temperature_2m,precipitation,wind_speed_10m \
  --open-meteo-base-url http://127.0.0.1:8080 \
  --output data/copenhagen_demo
```

Public Single Runs is not a reliable multi-model source. For multi-model
comparisons, use a validated self-hosted backend, previous-runs/historical
forecast APIs, or locally archived forecasts.

### 2. Verification Rows

Verification compares each forecast value with the observed value at the same
target time. The important join is:

- forecast issue time: when the forecast run was initialized
- forecast target time: when the forecast claims the weather happens
- lead hours: target time minus issue time
- observation time: measured/analysis time

The CLI path:

```bash
meteoright verify \
  --data-dir data/copenhagen_demo \
  --variables temperature_2m,precipitation,wind_speed_10m \
  --output data/copenhagen_demo/verification
```

Key functions:

- `verification.aligner.align_forecasts_with_observations()`
- `verification.errors.compute_error_columns()`
- `verification.provenance.verify_provenance_integrity()`
- `verification.validator.VerificationValidator`

The output has columns like:

- `forecast_temperature_2m`
- `observed_temperature_2m`
- `temperature_2m_error`
- `forecast_precipitation`
- `observed_precipitation`
- `precipitation_error`

### 3. Metrics

Metrics aggregate the verification rows by dimensions such as lead time, model,
month, and season.

```bash
meteoright metrics \
  --verification "data/copenhagen_demo/verification/*.parquet" \
  --group-by lead_hours,model \
  --variables temperature_2m,precipitation,wind_speed_10m \
  --metrics mae,rmse,bias,std \
  --output data/copenhagen_demo/metrics
```

Key functions:

- `metrics.aggregations.aggregate_metrics()`
- `metrics.metrics.mean_absolute_error()`
- `metrics.metrics.root_mean_squared_error()`
- `metrics.metrics.bias()`
- `metrics.validation.validate_metrics()`

The central comparison is usually:

- error vs lead time
- error by model
- error by month/season
- error by variable

## Spatial Grid Workflow

The spatial figures are not just one point. They repeat the same verification
workflow over a local grid around Copenhagen.

First identify grid points:

```bash
meteoright grid-points \
  --lat 55.605 --lon 12.574 \
  --radius-km 50 \
  --summary
```

Key functions:

- `forecast.grid_points.find_grid_points()`
- `forecast.grid_points.summarize_grid_points()`
- `forecast.plot_grid_points.plot_grid_map()`
- `forecast.plot_grid_points.plot_grid_comparison()`

The current grid-point helpers were originally written for ECMWF IFS / ERA5
0.25 degree grids. That is correct for `ecmwf_ifs025`, but it is not correct
for every self-hosted model domain.

Checked against the local Open-Meteo backend on 2026-06-05:

| Local domain | Returned grid near Copenhagen | Notes |
| --- | --- | --- |
| `ecmwf_ifs025` | 0.25 degree | e.g. requests near 55.605, 12.574 snap to 55.5, 12.5 or 55.75, 12.75 |
| `dwd_icon` | 0.125 degree | e.g. 55.605, 12.574 snaps to 55.625, 12.625 |
| `dwd_icon_eu` | 0.0625 degree | e.g. 55.605, 12.574 snaps to 55.625, 12.5625 |

The on-disk Open-Meteo metadata also shows different domains:

- `/home/mumrah/open-meteo-data/ecmwf_ifs025/static/meta.json`: global WGS84
  bbox `[-90.0, -180.0, 90.0, 179.75]`
- `/home/mumrah/open-meteo-data/dwd_icon/static/meta.json`: global WGS84 bbox
  `[-90.0, -180.0, 90.0, 179.75]`
- `/home/mumrah/open-meteo-data/dwd_icon_eu/static/meta.json`: regional WGS84
  bbox `[29.5, -23.5, 70.5, 62.5]`

The native-grid comparison asks:

> At each model grid point, how well does the forecast at that grid point match
> the observation/analysis data assigned to that point?

The interpolated comparison asks:

> If forecast fields are interpolated onto the observation points first, how
> does forecast error change?

That distinction matters because weather observations are mostly on land, while
forecast grids cover land and sea uniformly. Around coastlines, the nearest
native model grid point can represent a different surface regime than the
observation location.

## Interpolation Comparison

The interpolation figures compare native verification against verification after
forecast values are interpolated to the observation grid.

Important concepts:

- Native grid: compare forecast grid point to nearby observation/analysis point.
- Linear interpolation: estimate the forecast value at the observation point
  from surrounding forecast grid points.
- Nearest interpolation: use the nearest forecast grid point.
- IDW interpolation: inverse-distance weighted interpolation from surrounding
  forecast points.

For mixed-model interpolation, do not snap all coordinates to a 0.25 degree
grid. Interpolation should use the actual returned coordinates from the
self-hosted API for each model/domain. The safe approach is:

1. Query each model on its own native grid.
2. Preserve `model`, `latitude`, and `longitude` exactly as returned.
3. Build interpolation neighborhoods per model, not across models.
4. Interpolate each model to the observation locations independently.
5. Only compare models after they have been evaluated on the same observation
   points and lead windows.

`forecast.plot_error_grid._snap_to_025_grid()` and
`forecast.grid_points.GRID_SPACING_DEG` are therefore suitable only for
ECMWF/ERA5-style 0.25 degree plots. They should be generalized before using the
same spatial plotting path for `dwd_icon` or `dwd_icon_eu`.

Showcase files:

- `grid_interpolation_schematic.png`
- `wind_interpolation_effect.png`
- `wind_interpolation_effect_idw.png`
- `wind_composite_forecast_observation_grid.png`
- `wind_composite_interpolated_linear_nearest.png`
- `surface_composite_forecast_observation_grid.png`
- `surface_composite_interpolated_linear_nearest.png`

What is being compared:

- native-grid MAE vs interpolated MAE
- lead-window behavior before/after interpolation
- spatial error patterns before/after interpolation
- wind speed/gust/direction behavior near coastal grid points

## Error Maps and Spatial Error Surfaces

The lower-level spatial map helper is:

- `forecast.plot_error_grid.plot_error_map()`

It loads grid-run directories, computes MAE per grid point, snaps returned
coordinates to the 0.25 degree grid, and plots an error surface with
`scipy.interpolate.griddata()`.

Example shape:

```python
from forecast.plot_error_grid import plot_error_map

plot_error_map(
    data_dir="data/grid_runs/copenhagen_50km",
    variable="wind_speed_10m",
    metrics=["mae"],
    lead_hours=24,
    output="showcase/wind_error_map.png",
)
```

This helper is useful for exploratory spatial plots. The showcase composites are
more polished arrangements of the same ingredients: spatial error summaries,
lead-window summaries, and native-vs-interpolated comparisons.

## Event Verification

Event plots turn continuous forecast values into yes/no event forecasts, then
compute confusion counts.

Examples:

```bash
meteoright advanced events \
  --verification "data/copenhagen_demo/verification/*.parquet" \
  --event no_rain \
  --group-by lead_hours,model \
  --output data/copenhagen_demo/events

meteoright advanced events \
  --verification "data/copenhagen_demo/verification/*.parquet" \
  --event frost \
  --group-by lead_hours,model \
  --output data/copenhagen_demo/events
```

Key functions:

- `verification.events.generate_events()`
- `verification.confusion.compute_confusion_matrix()`
- `verification.confusion.compute_confusion_counts()`
- `verification.skill_scores.compute_skill_scores()`
- `verification.event_validation.validate_confusion()`
- `verification.event_validation.validate_skill_scores()`

Showcase files:

- `precipitation_event_confusion.png`
- `frost_event_confusion.png`
- `precipitation_event_investigation.png`

What is being compared:

- hits: forecast event happened
- misses: observed event happened, forecast missed it
- false alarms: forecast event did not happen
- correct negatives: no event forecast and no event observed
- skill scores such as hit rate, false alarm rate, precision, and CSI
- native-grid event verification vs interpolated event verification

## Current Reproducibility Caveat

The repo contains the reusable CLI, metric, event, grid-point, and plotting
functions listed above. The exact one-off scripts that assembled the final
publication-style composite PNGs in this folder are not currently present as
standalone source files. Recreating the precise final layouts therefore requires
either recovering those scripts or rebuilding a small composition layer on top
of the documented metric/verification outputs.

The important reproducible pieces are still present:

- data download and Parquet storage
- forecast/observation alignment
- error and metric computation
- event confusion matrices and skill scores
- grid-point discovery
- spatial error maps
- standard lead-time, seasonal, monthly, and distribution plots
